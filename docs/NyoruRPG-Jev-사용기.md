# RisuAI의 RPG 도구에 Jev를 붙여봤다 — 빨라진 판단과 아직 남은 생성 시간

> 이 글의 수치는 2026-10-08에 제공된 테스트 기록을 기준으로 한다. 이후 같은 0.30.0에 자료 준비·부분 생성·중복 검색 축소를 추가했으며, 그 변경의 시간과 비용은 아직 다시 측정하지 않았다.

나는 RisuAI에서 사용할 수 있는 NyoruRPG 플러그인을 만들고 있다. 메인 AI가 MCP 도구를 호출하면 플러그인이 주사위, 전투, 장비, 성장, 퀘스트 등을 계산하고 저장하는 시스템이다. 봇이 말로만 “아이템을 얻었다”, “적을 쓰러뜨렸다”고 하는 데서 더 나아가, 실제 데이터가 남는 TRPG 경험을 만드는 것이 목적이다.

이번에는 여기에 TypeSafe의 Jev를 연결했다. 목표는 플러그인 AI가 매번 긴 자료를 읽고 분류하는 부담을 줄이는 것이었다.

직접 플레이한 채팅, 호스트 진단, Jev 요청·응답 로그를 함께 살펴봤다. 결과부터 말하면 **Jev의 짧은 판단은 대부분 1초 안에 돌아왔다. 다만 새로운 장소나 인물을 작성하는 시간까지 사라진 것은 아니었다.** 무엇이 실제로 바뀌었고, 무엇은 아직 기대에 머물러 있는지 정리해보려 한다.

## 원래 NyoruRPG는 어떻게 작동하는가

기본적인 흐름은 다음과 같다.

```text
메인 AI가 MCP 호출
  → 플러그인이 현재 상태와 저장된 정의 확인
  → 기존 데이터로 처리할 수 있으면 엔진에서 계산
  → 새 인물·기술·장소 등의 작성이 필요하면 플러그인 AI 사용
  → 작성 결과를 규칙과 저장 형식에 맞게 확인
  → 실제 계산·저장 결과를 메인 AI에 반환
```

여기서 시간이 걸리는 부분은 단순 조회보다 새로운 데이터 준비였다. 플러그인 AI가 로어북과 기존 자료를 읽고 새 정의를 작성한 뒤, 시스템에서 사용할 수 있는 형태로 만드는 데 시간이 필요했다.

이전에 수집한 호스트 진단에는 다음과 같은 호출이 남아 있다.

| 호출 사례 | 전체 시간 | 그중 준비 단계 |
| --- | ---: | ---: |
| 탐험 | 51.1초 | 47.7초 |
| 인물 등록 | 50.7초 | 47.6초 |
| 아이템 획득 | 21.9초 | 17.4초 |

출처는 앞서 수집한 `RPG-호스트-진단 (13)`이다. 평균이나 대표 성능을 뜻하는 값이 아니라, 실제로 오래 걸린 호출 사례다. 준비 단계에는 자료 확인과 생성 AI 대기 등이 함께 들어가므로 이 시간을 전부 모델의 추론 시간이라고 볼 수도 없다.

플레이 중 체감으로는 답변 하나를 받는 데 몇 분씩, 전투가 길어지면 10분 가까이 기다리는 경우가 있었다. 전투는 도구 한 번으로 끝나지 않고 여러 행동을 연속해서 처리하기 때문이다. 그 사이에 새 적이나 새 기술까지 준비하면 대기가 더해진다. 여기에 메인 AI가 다음 호출을 판단하고 답변을 작성하는 시간도 들어간다.

해결하고 싶었던 문제는 세 가지였다.

- 분류나 검색처럼 간단한 일에도 생성 AI가 자료를 길게 읽는 문제.
- 새로운 게임 데이터를 작성하는 데 걸리는 시간.
- 플레이가 쌓이면서 필요한 인물·물품·로어북을 찾기 어려워지는 문제.

처음에는 임베딩 검색을 생각했다. 그러다가 짧은 판단과 분류에 특화됐다는 Jev를 알게 되어, 실제 플러그인에 붙여보기로 했다.

## Jev에 맡긴 일

처음에는 새 데이터 작성까지 Jev로 바꾸면 좋겠다고 생각했다. 그러나 Jev는 일반적인 챗봇처럼 긴 설명이나 새로운 캐릭터 JSON을 자유롭게 작성하는 모델이 아니다. 자료와 질문, 선택 기준을 주고 코드에서 사용할 구조화된 판단을 받는 방식이다. [TypeSafe 공식 소개](https://docs.typesafe.ai/introduction)

그래서 현재 구현은 다음처럼 역할을 나눴다.

| 작업 | 현재 담당 |
| --- | --- |
| 정확한 ID로 저장된 값 조회 | 플러그인 코드 |
| 로어북 후보의 관련성, 질문 주제, 기존 기술 후보 판단 | Jev 보조 |
| 새 캐릭터·기술·장소의 설명과 고유 설정 작성 | 기존 플러그인 AI |
| 주사위, 피해, 비용, 보상과 저장 검증 | 게임 엔진 |
| 실제 결과를 바탕으로 이야기 작성 | 메인 AI |

예를 들어 새 인물을 만들 때 Jev는 “이 로어북 조각이 해당 인물에게 필요한가?”, “기존 인물 중 확인할 후보가 있는가?”를 판단한다. 기술 요청에서는 “이미 가진 기술과 같은 요청인가?”, 물품에서는 “어떤 종류인가?”를 물을 수 있다.

뉴뉴가 사용자의 질문에 답할 때도 어떤 기능 설명을 참고해야 하는지 분류한다. ‘놓치지마 검사’에는 의심되는 누락 항목을 분류하는 보조 역할을 연결했다. 다만 Jev의 판단만으로 전체 검사를 생략하거나 게임 데이터를 바꾸지는 않는다.

즉, 지금 구현한 것은 **생성 AI가 해야 할 검색·선택의 일부를 앞에서 나누어 처리하는 구조**다. 새 데이터의 작성 전체를 Jev로 대체한 것은 아니다. 필요한 후보를 못 찾거나 판단이 모호하면 원래 처리로 이어진다.

## 어떻게 질문하고 응답을 사용하는가

Jev에 보내는 질문과 선택 기준은 영어로 작성했다. 캐릭터 이름과 로어북, 채팅 등 판단할 자료는 원문 그대로 전달한다. 공식 문서도 영어가 가장 강한 언어이며 한국어 등 다른 언어는 실제 자료로 검증하라고 안내한다. 영어로 질문했다고 한국어 원문에 대한 판단까지 검증된 것은 아니다. [언어 지원 안내](https://docs.typesafe.ai/models)

실제 로그에는 다음 사례가 있다. 요청 내용은 보기 쉽게 필요한 필드만 발췌했다.

```text
대상: 바람결 숲 외곽 능선
설명: 과수원 서쪽 개구멍을 통해 능선길로 진입하여 수련을 시작한다.

질문:
What environment is explicitly indicated for this requested place?

선택지:
settlement / wilderness / interior / mixed / uncertain
```

응답의 핵심 값은 다음과 같았다.

```json
{
  "choice": "wilderness",
  "confidence": 0.96,
  "probabilities": {
    "settlement": 0,
    "wilderness": 0.97,
    "interior": 0,
    "mixed": 0.03,
    "uncertain": 0
  }
}
```

이 요청은 **858ms**에 돌아왔다. 입력은 897토큰, 출력은 60토큰으로 보고됐다. 능선길을 자연 야외 지형으로 분류한 것은 제공된 설명과 맞았다.

하지만 이 응답이 지도 전체를 만든 것은 아니다. 기존 생성 AI에 환경 분류를 참고 정보로 전달했고, 구역과 연결, 장치 등은 여전히 생성 AI가 작성했다. 또한 `confidence: 0.96`은 모델이 보고한 확신도이지, 실제 정답률을 측정해 96%라고 인증한 수치가 아니다.

반대로 주의가 필요한 사례도 있었다. **‘바람칼날 매’**를 준비하는 요청에 Jev가 기존 **‘질풍의 칼날발톱’**을 정체성 확인 후보로 지목했고, 확신도는 0.89였다. 자료만으로 두 대상이 같은 개체라고 확정할 근거는 부족했다.

현재 이 판단은 후보 추천일 뿐 자동 병합 명령이 아니다. 로그에서도 실제로 두 인물이 합쳐졌다고 확인된 것은 아니다. 그래도 새 몬스터 개체라는 정보가 명확한 요청에는 이런 추천이 필요하지 않으므로, 개체 식별자가 지정된 신규 생성에서는 정체성 추천을 건너뛰도록 보완했다.

이 사례를 보며 확실해진 점은, **응답이 빠르고 형식이 정확해도 내용의 검증은 따로 필요하다**는 것이다.

## 사용 방법

NyoruRPG의 **AI 연결 → Jev 빠른 판단**에서 설정할 수 있다. 기본적으로는 꺼져 있다.

1. Jev를 지원하는 API 주소·키·모델을 입력하거나 **기본 API 사용**을 선택한다.
2. **Jev 사용**을 켠다.
3. 로어북 검색, 데이터 준비, 뉴뉴 질문 분류, 검사 보조, 초간단 질문 중 사용할 영역을 선택한다.
4. **Jev 설정 저장**을 누른다.

TypeSafe에 직접 연결하는 기본 주소는 `https://api.typesafe.ai/v1/systemone`이다. 기본 API를 공유하면 `/v1/chat/completions` 같은 생성 경로를 `/v1/systemone`으로 바꾸고 Jev 요청의 모델을 `jev`로 설정한다. 따라서 사용하는 프로바이더가 해당 경로와 모델을 지원해야 한다. 주소와 키만 같다고 모든 프로바이더에서 자동으로 지원되는 것은 아니다.

> [스크린샷 자리: Jev 연결 설정과 영역별 토글]

추가한 **초간단 질문**은 “이 물건 얼마야?”, “남은 화살 몇 발이야?”처럼 저장값을 짧게 조회하는 용도다. Jev가 해당 자료를 고르면 플러그인이 실제 저장값으로 답한다. 대상이 모호하면 기본 플러그인 AI가 해석한다.

가격을 새로 지어내거나 거래를 실행하지는 않는다. 가격 조회는 저장된 기준 가치이며, 실제 거래 할인·수수료와는 구분한다. 에렌샤 현실모드의 숨겨진 욕구는 공개 가능한 생활 경고 범위에서만 답한다.

## 무엇을 기준으로 평가했는가

AI가 “잘 처리했다”고 말한 것만으로 성공을 판단하지 않았다. 다음 자료를 함께 봤다.

- Jev에게 실제로 보낸 자료와 질문.
- 실제 응답의 선택, 확신도, 사용량, 시간.
- 플러그인이 그 응답을 채택했는지, 기존 처리로 넘겼는지.
- 호스트에 남은 도구 완료 기록과 각 단계의 시간.
- 그 시점의 채팅과 서술 내용.

최신 Jev 진단에는 이전 실험이 누적돼 있었다. 그래서 `전체진단 (4)`의 39건을 전부 새 실험으로 세지 않고, 이전 `(3)`에 없던 **14건**을 따로 뽑았다. 현재 채팅 진단과 전체 진단에 같은 요청이 들어 있는 것도 중복 집계하지 않았다.

게임 호출은 별도로 **‘챕터 6: 창공을 가르는 간합’, Chatindex 42~53**을 확인했다. Jev 14건의 시간 범위는 이 채팅 구간보다 넓다. 아래 두 표는 같은 모집단이 아니며, Jev 14번이 MCP 21번과 일대일로 대응하는 것도 아니다.

또한 0.29.10이라는 같은 버전 안에서도 수정하며 이어서 테스트했다. 동일한 입력으로 Jev ON/OFF를 비교한 실험은 아니므로 전체 속도나 비용의 절감률은 계산하지 않았다.

## 실제 응답 시간

새 Jev 요청 14건은 모두 HTTP 200으로 돌아왔고, 응답 형식도 정상적으로 읽혔다.

| 항목 | 측정값 |
| --- | ---: |
| 새 요청 수 | 14건 |
| 가장 짧은 응답 | 0.505초 |
| 중앙값 | **0.690초** |
| 평균 | 0.891초 |
| 가장 긴 응답 | 3.046초 |
| 보고된 입력 사용량 | 74,553토큰 |
| 보고된 출력 사용량 | 7,665토큰 |

용도별로 보면 차이가 있었다.

| 용도 | 요청 수 | 중앙값 | 실제 후속 처리 |
| --- | ---: | ---: | --- |
| 뉴뉴 주제 분류 | 6건 | 0.641초 | 주제 선택 경로 4건, 기존 처리 전환 2건 |
| 생성 준비 | 5건 | 0.702초 | 구성 요소 힌트 2건, 기존 처리 전환 3건 |
| 로어북 의미 검색 | 3건 | 1.082초 | 모두 기존 검색·해석으로 전환 |

**14건 정상 응답은 정답률 100%라는 뜻이 아니다.** 구성 요소 힌트 중에는 앞서 설명한 정체성 후보도 들어 있다. 주제 선택 역시 정답셋으로 평가한 정확도가 아니라 플러그인이 선택한 처리 경로다.

‘기존 처리로 전환’도 연결 오류와는 다르다. Jev 응답은 받았지만 관련 후보를 충분히 확신하지 못했거나, 요청에 필요한 내용을 고르지 못해 원래 AI가 처리한 경우다. 이 구분을 하지 않으면 정상적인 보류를 API 실패로 오해하기 쉽다.

## 전체 플레이는 얼마나 빨라졌는가

Chatindex 42~53에서 호스트 진단과 연결된 게임 도구 호출은 **21건**이었다. 이 21건은 모두 완료됐고, 기록상 타임아웃이나 도구 결과가 돌아오기 전에 답변이 끝난 사례는 없었다.

전체 호출의 중앙값은 **4.31초**였다. 그중 준비 단계가 1초 미만인 18건만 보면 중앙값은 **4.18초**였다. 기존 자료를 처리하는 호출에도 호스트 상태 확인·동기화·저장 등의 시간이 남아 있었다.

새 데이터를 준비하는 호출은 여전히 오래 걸렸다.

| 최신 구간의 호출 | 전체 시간 | 준비 단계 |
| --- | ---: | ---: |
| 새 탐험 시작 | 50.5초 | 47.2초 |
| 탐험 상호작용 | 22.1초 | 18.7초 |
| 이동 중 새 조우 준비 | 59.6초 | 55.3초 |

이 결과로는 “Jev가 0.7초에 답하니 탐험 생성도 0.7초가 됐다”고 말할 수 없다. Jev의 판단이 짧아도 기존 생성 AI가 작성하는 구간은 그대로 남는다. Jev가 보류하고 원래 AI까지 호출하면 대기가 하나 추가될 수도 있다.

채팅 본문에는 호스트 요청과 연결하지 못한 도구 표시도 4개 있었다. 실제 요청 인자나 결과가 남아 있지 않아 표시 과정의 문제인지, 다른 단계의 재시도인지 이번 자료로는 확정하지 못했다. 따라서 채팅에 보이는 모든 도구 표시가 검증됐다고 하지는 않겠다.

## 유사도와 응답의 질

로어북 검색에서 중요한 것은 문장이 비슷한지보다 **지금 필요한 원문을 제대로 찾아왔는지**다. 바람을 사용하는 새 몬스터와 기존 바람 계열 보스는 묘사가 비슷할 수 있지만, 같은 인물이라는 뜻은 아니다.

이번 로어북 요청 3건은 모두 기존 처리로 넘어갔다. 그러므로 이 결과로 검색 정확도가 올랐다거나, 뉴뉴의 로어북 비용이 크게 줄었다고 말하기는 어렵다. 정답으로 삼을 원문 목록을 만든 뒤 필요한 자료를 얼마나 찾았고 불필요한 자료를 얼마나 제외했는지 확인해야 한다.

이번에 확인한 품질은 좀 더 제한적이다. 응답 형식은 정상적으로 읽혔고, 지형 분류가 자료와 맞는 사례가 있었다. 반면 정체성 판단은 검증이 필요했고, 불확실할 때 기존 처리로 넘기는 경로도 실제로 사용됐다.

서술 문장의 재미나 완성도는 여전히 메인 AI의 역할이다. Jev의 JSON 응답 품질과 최종 소설의 품질을 같은 지표로 평가하지 않았다.

## 가격은 어느 정도였는가

2026년 10월 8일 확인한 TypeSafe의 `jev-1.13.0` 직접 API 공개 가격은 **입력 100만 토큰당 $0.042**, 출력은 무료다. [공식 모델·가격 안내](https://docs.typesafe.ai/models)

이를 이번 14건의 보고된 입력 사용량에 적용하면 다음과 같다.

```text
74,553 ÷ 1,000,000 × $0.042 = 약 $0.00313
```

이것은 **공식 직접 API 가격을 적용한 참고 계산**이다. 테스트에 사용한 프로바이더의 실제 청구서나 별도 요율을 확인한 금액은 아니다. 메인 AI와 생성 AI의 비용도 포함하지 않았다.

Jev 요청 자체의 참고 비용은 작았다. 하지만 전체 지출이 줄었는지는 별개의 문제다. 기존 AI에 보내는 자료나 호출이 실제로 줄어야 절감이 생긴다. 이번에 채택된 두 구성 요소 힌트의 기록에서는 원문 제거량이 0이었고, 생성 AI를 대체했다고 확인되지도 않았다. 따라서 절감률을 숫자로 붙이지 않았다.

## 적용하면서 신경 쓴 부분

자료가 길어졌을 때는 입력 한도도 문제가 됐다. 이전 테스트에서 보였던 일부 `JEV_LIMIT`는 서버가 실패한 것이 아니라, 플러그인이 전송 전에 정한 입력량을 초과해 요청을 보내지 않은 경우였다.

현재는 독립적인 질문들을 여러 묶음으로 나누어 보낸다. 각 묶음의 요청과 응답을 기록하고, 모두 완료된 결과만 합친다. 하나의 질문에 필요한 선택지를 임의로 둘로 쪼개 의미를 바꾸거나, 실패한 게임 행동을 다시 실행하지는 않는다. 분할하면 호출 수와 반복 입력량이 늘 수 있다는 점도 함께 봐야 한다.

또한 모델의 판단과 실제 게임 데이터 변경 사이를 분리했다. Jev가 인물을 지목했다고 즉시 병합하거나, 퀘스트가 끝났다고 판단했다고 바로 보상을 주게 만들지 않았다. 원문·현재 상태·기존 영수증과 게임 규칙을 확인하는 단계가 남아 있다.

제보용으로는 실제 요청·응답, 후속 선택, 오류와 소요 시간을 보관한다. 인증정보는 가리지만 원문 채팅과 로어북이 들어갈 수 있으므로 공개 게시물에는 필요한 예시와 집계만 옮겼다.

## 앞으로 RisuAI에서 활용해볼 방향

### 1. 로어북 검색의 두 번째 판단 단계

키워드나 임베딩으로 후보를 찾은 다음, Jev에게 “이 자료가 지금 요청한 인물이나 상황을 설명하는가?”를 물어볼 수 있다. 임베딩을 없애는 방식이라기보다 후보 검색 뒤의 추가 판별에 가깝다. TypeSafe의 공식 재정렬 예제도 먼저 후보를 좁힌 뒤 각 후보와 질문을 비교한다. 후보 목록에 들어오지 않은 원문은 이 단계에서 찾아낼 수 없다. [공식 검색 재정렬 예제](https://docs.typesafe.ai/cookbooks/rerank_typesafe)

NyoruRPG에도 의미 검색 경로를 연결했지만, 이번 한국어 로어북 자료에서 효율 개선이 입증된 단계는 아니다. 후보 구성과 질문을 더 다듬을 여지가 있다.

### 2. 상태창과 간단한 질의응답

“이 아이템 얼마야?”, “누가 재사용 대기 중이야?”처럼 범위가 좁고 답이 이미 저장돼 있는 질문은 잘 맞는 활용처라고 생각한다. 대상을 선택하는 판단만 맡기고, 숫자는 저장소에서 읽으면 된다.

장비 조건이나 관계 사건의 분류에도 응용할 수 있다. 다만 “좋아 보인다”는 문장만으로 호감도를 마음대로 바꾸기보다는, 사건 분류와 실제 수치 적용을 나누고 봇이 정한 규칙을 따라야 한다.

### 3. 메모리의 사실 후보 분류

기존 사실과 같은 내용인지, 새 사실인지, 서로 충돌하는지 후보를 분류하는 데 활용할 수 있다. 이름이 비슷한 인물이나 과거·현재 시점이 다른 정보를 섞지 않도록 원문과 시점을 보관하는 것이 중요하다.

이는 앞으로 응용할 수 있는 방향이며, 이번 NyoruRPG 실험으로 별도의 장기기억 시스템 성능을 검증한 것은 아니다.

### 4. 다음에 필요할 데이터의 사전 준비

새 장소가 언급됐을 때 필요한 자료 후보를 미리 골라두면, 실제 도구 호출이 들어온 뒤의 작업을 줄일 가능성이 있다. 정해진 템플릿을 선택해 코드로 조립하는 범위를 넓히는 것도 생각해볼 수 있다.

다만 서술이 출력되는 즉시 모든 데이터를 확정 저장하면, 사용자가 답변을 리롤하거나 삭제했을 때 잘못된 내용이 남을 수 있다. 먼저 준비해둔 후보와 확정된 게임 상태를 구분하고, 실제 채택된 답변에 맞춰 적용해야 한다. **이번 버전이 모든 채팅을 백그라운드에서 읽으며 자동 갱신하는 것은 아니다.**

### 5. MCP에서 짧은 조회와 긴 생성을 구분하기

정확한 ID와 계산식으로 처리할 수 있는 요청은 코드가 바로 처리하고, 의미 해석이 필요한 부분만 Jev에 맡기는 방향이 적합해 보인다. 새로운 설명과 고유 규칙이 필요한 경우에는 생성 AI가 필요하다.

모든 호출 앞에 Jev를 한 번씩 붙이면 빠른 조회까지 느려질 수 있다. 무엇을 맡길지 선택하는 설계가 모델 자체의 응답 속도만큼 중요했다.

기대했던 세 가지 목표는 현재 이렇게 평가하고 있다.

| 새 데이터 작성 시간 없애기 | 달성하지 못함. 새 장소·조우 준비에 47~55초가 남음 |

Jev를 붙여보며 확인한 가능성은 **저렴한 짧은 판단을 게임 도구의 앞단에 배치할 수 있다는 것**이다. 동시에 데이터 생성, 저장 동기화, 메인 AI의 다음 행동 판단까지 한꺼번에 해결해주는 것은 아니라는 점도 확인했다.

제공된 플레이 기록을 확인하고 발견한 저장·편집·조회 문제를 보완한 뒤, 관련 로컬 자동 검사 101개를 통과한 내용으로 NyoruRPG 0.30.0을 준비했다. 이 검사는 실제 RisuAI 설치 실행이나 유료 모델 재시험과는 구분한다. 이번 실사용 구간에는 ‘놓치지마 검사’와 ‘초간단 질문’의 Jev 실행 기록이 없어 두 기능의 실사용 효과까지 확인한 것은 아니다.

다음에는 같은 저장 상태와 같은 요청을 준비해 Jev ON/OFF를 비교하려 한다. 후보를 얼마나 정확하게 골랐는지, 생성 AI 입력과 호출이 실제로 얼마나 줄었는지, 최종 답변까지 걸린 시간과 전체 비용이 어떻게 달라지는지를 함께 봐야 이 실험의 효과를 더 정확히 말할 수 있을 것 같다.
